Connexion : champs requis

Le formulaire e-mail/mot de passe refuse localement avant tout appel réseau. Le test porte sur l'e-mail trimé et sur le mot de passe brut.

if (!email.trim() || !password) {
  setMessage('Renseignez l’e-mail et le mot de passe.');
  return;                      // aucun appel réseau
}
void run(() => signInWithPassword(email, password));

// run(action) : setMessage(''), setIsBusy(true)
//   try   { await action() }            // aucune navigation : AuthGate bascule seul
//   catch { setMessage(authErrorMessage(code ?? '')) }
//   finally { setIsBusy(false) }

// signInWithPassword : signInWithEmailAndPassword(auth, email.trim(), password)

Deux filtres du navigateur précèdent ce test. Le champ est un <input type="email"> : l'algorithme de normalisation de valeur du HTML retire les sauts de ligne puis les espaces de tête et de queue avant que onChange ne lise e.target.value — l'état ne contient donc jamais les espaces que trim() est censé écarter, et les deux trim() (le test, l'envoi) ne mordent que sur une valeur déjà normalisée. Le <form> n'a pas noValidate : la validation native refuse une adresse mal formée et handlePasswordSubmit n'est alors pas appelé.

Le mot de passe part tel quel, espaces compris. Les deux boutons portent disabled={isBusy} pendant l'appel.

src/features/auth/LoginPage.tsx, src/shared/platform/auth.ts

Cas limites
  • E-mail composé d'espaces : la normalisation du champ le vide, l'état vaut '' → message local, aucun appel.
  • Mot de passe d'un seul espace : chaîne non vide → l'appel part et Firebase répond auth/invalid-credential.
  • Adresse syntaxiquement invalide : la validation native bloque la soumission — ni message de l'application, ni appel.
  • Bouton Google : hors du <form>, aucun champ n'est testé, run(signInWithGoogle) part directement.
  • Succès : aucune redirection n'est écrite ici ; c'est AuthGate qui repasse en signedIn et rend l'application.

Camille colle « camille@exemple.fr » : le navigateur retire les espaces avant React, l'état porte déjà « camille@exemple.fr », et le trim() du code n'a plus rien à retirer.

Verrou actif

Le verrou n'a pas de réglage : il se déduit de la clé d'API de la configuration.

export const isAuthConfigured = FIREBASE_CONFIG.apiKey !== '';
export const isDatabaseConfigured = isAuthConfigured;   // firestore.ts

La configuration du dépôt porte apiKey: 'AIzaSyAww…', projet glow-private : le verrou est actif. AuthGate ne monte le hook d'authentification que si isAuthConfigured ; sinon il rend ses enfants tels quels. L'objet Auth est construit au premier usage et jamais à l'import : sans configuration, aucun appel réseau ni stockage Firebase n'existe, et getFirebaseAuth() lèverait une Error.

src/shared/platform/firebase.config.ts, src/shared/platform/firestore.ts, src/features/auth/AuthGate.tsx

Cas limites
  • Configuration vide : currentAuthUser() rend null sans lever — l'absence de compte n'est pas un incident.
  • Configuration vide : l'application s'ouvre sans page de connexion, et la suppression de compte saute l'étape Firebase.
  • Une clé d'API remplie mais fausse n'éteint pas le verrou : elle le laisse actif et fait échouer chaque connexion.

Verrou et session Firebase

useAuth() part en loading et s'abonne à onAuthStateChanged. Le premier rappel arrive quand le SDK a fini de restaurer (ou non) la session mémorisée ; l'état devient alors signedIn avec { id, email, name }, ou signedOut. L'attente existe pour ne pas éclairer la page de connexion à une session déjà ouverte.

AuthGate :
  isAuthConfigured === false      → children
  status === 'loading'            → dégradé + point animé (aria-label « Chargement »)
  status === 'signedOut'          → LoginPage
  status === 'signedIn'           → children

La persistance est celle du SDK par défaut : getAuth() passe [indexedDBLocalPersistence, browserLocalPersistence, browserSessionPersistence], dans cet ordre. La session survit donc à la fermeture de l'onglet et n'a pas de durée limite ; seule une déconnexion explicite l'efface. L'application n'expose qu'un chemin de déconnexion : signOutUser(), appelé par le bouton « Se reconnecter » du bloc de suppression.

src/features/auth/useAuth.ts, src/features/auth/AuthGate.tsx, src/shared/platform/auth.ts

Cas limites
  • IndexedDB indisponible (navigation privée de certains navigateurs) : le SDK retombe sur localStorage, puis sur sessionStorage — dans ce dernier cas la session ne survit pas à la fermeture de l'onglet.
  • L'application ne sonde ni ne renouvelle rien : useAuth ne fait que s'abonner à onAuthStateChanged. Un compte supprimé ou désactivé depuis la console ne fait donc pas revenir la page de connexion par ce seul fait ; le SDK ne constate l'invalidation qu'au renouvellement d'un jeton.
  • currentAuthUser() ne s'abonne pas : il lit currentUser à l'instant et rendrait null s'il était appelé avant la fin de la restauration.

Camille s'est connectée en mai 2026. Chaque lancement depuis passe par l'état loading, le temps du premier rappel, puis signedIn avec son uid et son adresse.

Clé et format de la sauvegarde

AppData entier est écrit en un seul JSON sous STORAGE_KEY = 'glp1_app_companion_data', par un effet dépendant de appData.

useEffect(() => {
  if (!mayPersist(loadFailed.current)) return;
  setItem(STORAGE_KEY, appData);      // localStorage.setItem(key, JSON.stringify(value))
}, [appData]);

L'effet s'exécute aussi au montage, avant toute modification : c'est cette écriture initiale que le garde-fou du chargement doit bloquer. Il n'y a ni écriture différée, ni fusion, ni numéro de version dans le document : la valeur écrite remplace la précédente en entier.

Le reste de ce que l'application retient vit sous d'autres clés — un grep sur src rend 42 chaînes littérales distinctes glp1_*, glow_* et hasAcceptedMedicalDisclaimer_v1, déclarées dans 32 fichiers hors tests, administration et thèmes compris. Deux d'entre elles portent du domaine (aliments créés, menus favoris) ; les autres sont des réglages, des drapeaux et des compteurs. Aucune ne passe par AppData.

src/app/useAppData.ts, src/shared/platform/storage.ts

Cas limites
  • Quota dépassé : setItem avale l'exception, la sauvegarde en mémoire diverge de celle du stockage sans aucun signe à l'écran.
  • Chaque changement d'état réécrit le document entier, même pour un champ : la taille écrite est celle de tout le suivi.

Camille corrige son objectif de poids : l'effet réécrit sous la même clé le JSON complet — profil, pesées depuis mai 2026, injections d'Ozempic, effets secondaires — et non le seul champ modifié.

Ordre de conversion au chargement

Le chargement lit la clé en chaîne nue (getString) puis analyse lui-même le JSON, pour distinguer une sauvegarde absente d'une sauvegarde illisible. Les suppressions de champs précèdent la fusion du profil, qui précède la chaîne de migrations.

saved = getString(STORAGE_KEY)          // null ou '' → profil d'usine, sans échec
parsed = JSON.parse(saved)

delete parsed.waterLogs                 // suivi hydrique, supprimé le 2026-08-07
delete parsed.milestones                // objectifs à paliers, supprimés le 2026-08-09
if (parsed.profile) {
  delete parsed.profile.hydrationTrackingEnabled
  delete parsed.profile.dailyWaterGoalMl
  delete parsed.profile.weightGoalsEnabled
}

hydrated = {
  ...parsed,
  profile:    { ...INITIAL_PROFILE, ...parsed.profile,
                avatar: { ...INITIAL_PROFILE.avatar, ...(parsed.profile?.avatar || {}) } },
  savedMeals: dropPreMigrationMeals(parsed.savedMeals),
  stepLogs:   parsed.stepLogs || [],
}

return ensureStartingWeighIn(
         fillMealHunger(
           mergeTableTennisSport(
             mergeSideEffectNotes(
               purgeDeleted(
                 migrateTreatmentIds(
                   dropSeedData(hydrated)))))))

L'ordre d'application est donc, du premier au dernier :

  1. dropSeedData — retire les lignes dont l'id commence par se-seed-, dl-s-, step-seed-, sport-seed- ou meal-seed-, sur les neuf listes, et matérialise à [] celles qui manquent.
  2. migrateTreatmentIds — profile.glp1Brand = toTreatmentId(…) ?? DEFAULT_TREATMENT_ID ; chaque injection.brand = toTreatmentId(brand), undefined conservé (il signifie « celui du profil »).
  3. purgeDeleted — retire les lignes portant un deletedAt non nul et retire le champ des autres. Sept listes seulement : meTimeLogs et sleepLogs n'en ont jamais porté.
  4. mergeSideEffectNotes — replie description dans notes : notes = rest.notes || description || undefined. notes l'emporte ; une description vide ne crée pas de note vide.
  5. mergeTableTennisSport — remplace les anciens noms de sport par MERGED_TABLE_TENNIS, le nom d'un sport étant sa clé au catalogue des MET.
  6. fillMealHunger — pose hungerBefore et hungerAfter sur les repas qui n'ont pas les deux en number ; un repas complet n'est jamais retouché.
  7. ensureStartingWeighIn — pose isStartingWeight sur toutes les lignes (w.isStartingWeight ?? w.id === 'starting-weight-log') ; si une ligne le porte, s'arrête là ; sinon, et seulement si l'ancien profil porte un startingWeight > 0, crée la pesée de départ et retrie par byDateTimeAsc.

Les sept fonctions sont idempotentes : les rejouer sur des données déjà converties ne change rien. Six sont pures ; la septième ne l'est pas — ensureStartingWeighIn(data, now = new Date()) est appelée sans now par la chaîne de chargement, et lit donc l'horloge de la machine par dateDeDepartParDefaut quand elle doit fabriquer une pesée de départ.

Le résultat de la conversion est réécrit dans le stockage immédiatement : l'effet de persistance dépend de appData et s'exécute au premier rendu, sans aucun geste. La sauvegarde convertie remplace donc l'ancienne dès le chargement — sauf gel du garde-fou.

src/app/useAppData.ts, src/shared/model/appData.ts, src/shared/model/purgeDeleted.ts, src/shared/model/startingWeighIn.ts

Cas limites
  • Sauvegarde valant la chaîne 'null' : JSON.parse réussit, delete parsed.waterLogs lève une TypeError — la sauvegarde est traitée comme illisible.
  • Sauvegarde valant un scalaire ou un tableau ('0', '[]') : le delete passe, ...parsed n'apporte rien, et l'on obtient le profil d'usine avec un journal des pesées vide — sans pesée de départ, ensureStartingWeighIn n'en créant une que depuis un ancien profile.startingWeight.
  • Chaîne vide : if (saved) est faux — profil d'usine et pesée semée, sans passer par le catch.
  • Plusieurs lignes marquées isStartingWeight : ensureStartingWeighIn ne corrige rien, et findStartingWeighIn retient la première du tableau.
  • Un champ inconnu de la sauvegarde traverse ...parsed intact et sera réécrit à la prochaine écriture.

Couche de stockage

Un seul fichier appelle localStorage ; il expose six fonctions, toutes muettes en cas d'erreur.

FonctionEffetSur erreur
getItem<T>(key)JSON.parse de la valeurnull — clé absente et contenu invalide sont indiscernables
setItem<T>(key, value)JSON.stringify puis écriturerien, en silence
getString(key)la chaîne telle quellenull
setString(key, value)la chaîne telle quellerien, en silence
removeItem(key)retire la clérien, en silence
clearAll()localStorage.clear()rien, en silence

Les deux familles ne sont pas interchangeables : setItem ré-encoderait un drapeau true en "true" et rendrait illisibles les valeurs déjà écrites en chaîne nue. La sauvegarde principale n'emprunte pas getItem à la lecture : elle passe par getString puis JSON.parse, précisément parce que getItem confond absence et illisibilité — distinction dont dépend le garde-fou.

clearAll efface en bloc plutôt que clé par clé : la liste des clés est éparpillée dans 32 fichiers, et une liste écrite à la main laisserait survivre la première clé ajoutée ailleurs. Le commentaire du fichier dit « une vingtaine » ; le compte s'est fait depuis.

Cas limites
  • Stockage indisponible (mode privé, quota) : toute lecture rend null, l'application démarre sur le profil d'usine et n'enregistre rien, sans message.
  • getItem sur une valeur écrite par setString : JSON.parse('true') rend true, mais JSON.parse d'un identifiant de thème lèverait et rendrait null.
  • clearAll ne se limite pas aux clés de l'application : il vide l'origine entière.

Garde-fou du chargement

Une lecture ratée ne doit pas écraser ce qu'elle n'a pas su lire : c'est l'effacement réel du 2026-08-17, causé par l'écriture au montage de l'effet de persistance. Le catch du chargement fait trois choses, dans cet ordre.

catch (e) {
  console.error(…)
  loadFailed.current = true                       // une ref, pas un état :
                                                  // l'effet la relit au même rendu
  if (getString(rescueKeyFor(STORAGE_KEY)) === null)
    setString(rescueKeyFor(STORAGE_KEY), saved)   // la chaîne BRUTE, une seule fois
}
// puis : retour de l'état initial (profil d'usine + pesée semée à 95 kg)

rescueKeyFor(k)       = `${k}__secours`
mayPersist(loadFailed) = !loadFailed
unreadableSaveNotice(k) = 'La sauvegarde n’a pas pu être lue. Elle a été mise à l’abri
  sous la clé « <clé>__secours » et RIEN ne sera enregistré tant que cet écran
  n’aura pas été rechargé : vos données ne sont pas effacées.'

La condition de mise à l'abri est === null, donc « clé absente » : une clé de secours présente mais vide empêche le sauvetage. Le message est posé par un effet à montage unique dans limitNotice, l'état qui sert aussi aux refus de plafond ; le bloc qui l'affiche porte donc le titre « Limite atteinte » et se ferme par dismissLimitNotice.

La portée du gel est exactement d'une écriture : mayPersist n'a qu'un appelant, l'effet qui écrit STORAGE_KEY. Les autres clés — acceptation médicale, aliments créés, menus favoris, menu, thème, vues d'historique, compteurs — continuent d'être écrites pendant la session.

Ordre de la suppression de compte

Trois états locaux : step ('idle' | 'confirming' | 'working'), message, needsFreshLogin. Le geste de confirmation supprime le compte avant les données ; un échec du compte laisse tout en place.

confirm() :
  message = '' ; needsFreshLogin = false ; step = 'working'
  try {
    if (isAuthConfigured) await deleteCurrentUser()
  } catch (e) {
    code = e.code ?? ''
    message        = accountDeletionErrorMessage(code)
    needsFreshLogin = (code === 'auth/requires-recent-login')
    step            = 'confirming'
    return                       // rien n'est effacé
  }
  clearAll()                     // localStorage.clear()
  reloadApp()                    // window.location.reload()

reconnect() :                    // bouton « Se reconnecter »
  signOutUser().catch(() => undefined).then(reloadApp)   // ne touche à aucune donnée

L'ordre est imposé : effacer avant de savoir laisserait une personne sans données mais avec un compte. reloadApp est un simple window.location.reload() ; la page de connexion réapparaît parce que deleteUser a déconnecté et que le verrou est actif — sans configuration Firebase, le rechargement rouvre directement l'application, sur le profil d'usine et l'avertissement médical.

reconnect enchaîne reloadApp après le catch : la page est rechargée même si la déconnexion échoue.

Cas limites
  • Sans configuration Firebase : l'étape compte est sautée, clearAll() et reloadApp() s'exécutent quand même.
  • Pendant 'working' : « Supprimer définitivement », « Annuler » et la croix portent disabled, et le premier affiche « Suppression… ».
  • Échec : retour à 'confirming', la mise en garde reste ouverte, le message s'affiche au-dessus des boutons ; « Annuler » et la croix le remettent à zéro.
  • clearAll() échoue en silence : le rechargement se ferait alors sur des données intactes, sans message — le compte, lui, n'existe plus.

Suppression du compte Firebase

deleteCurrentUser() encapsule le SDK et ajoute un code maison quand personne n'est connecté.

export const deleteCurrentUser = async (): Promise<void> => {
  const user = getFirebaseAuth().currentUser;
  if (!user) throw { code: 'auth/no-current-user' };   // code maison
  await deleteUser(user);
};

deleteUser côté SDK : obtient un jeton d'identité, appelle deleteAccount, vide le jeton de rafraîchissement, puis termine par auth.signOut(). La déconnexion est donc faite par le SDK, dans la foulée, sans appel supplémentaire.

auth/requires-recent-login est le cas courant et non un incident : la session est mémorisée sans limite de durée, et Firebase refuse une suppression sur une session ancienne. C'est pourquoi le bloc propose « Se reconnecter » sur ce seul code.

src/shared/platform/auth.ts, @firebase/auth 1.13.4

Cas limites
  • Verrou inactif : deleteCurrentUser n'est pas appelé — getFirebaseAuth() lèverait une Error sans champ code, qui tomberait sur le message par défaut.
  • auth/no-current-user est un objet nu { code }, pas une Error : seul le champ code est lu par l'appelant.
  • Réseau coupé pendant deleteAccount : le compte peut avoir été supprimé côté serveur sans que le signOut final ait lieu ; le catch du bloc s'exécute et rien n'est effacé localement.

Stockage local

clearAll() est localStorage.clear() : il vide l'origine entière, sans liste de clés. Il emporte donc glp1_app_companion_data, sa clé de secours si elle existe, glp1_user_custom_foods, glp1_favorite_meals, hasAcceptedMedicalDisclaimer_v1, et les 42 clés glp1_* et glow_* — menu, thème, sports et effets suivis, vues d'historique, paliers de badges, retours et sondage locaux, date de première ouverture.

Il n'emporte en revanche pas la session Firebase par lui-même : le SDK persiste d'abord dans IndexedDB, que localStorage.clear() ne touche pas. La session disparaît parce que deleteUser appelle signOut(). Le commentaire de storage.ts qui attribue la disparition de la session à clearAll est inexact ; il ne le serait pas dans le cas de repli où IndexedDB est indisponible et où le SDK écrit dans localStorage.

Cas limites
  • Sans configuration Firebase, clearAll() est le geste entier : il n'y a pas de session à défaire.
  • Ce qui survit à clearAll : IndexedDB, sessionStorage, les cookies, et le contenu des autres origines.
  • L'acceptation médicale partant avec le reste, le rechargement qui suit la suppression rouvre l'application sur le premier lancement légal.
