16. Les équivalences insolites ↑ sommaire

Ce chapitre décrit le moteur qui traduit un nombre de kilos en un ou deux objets d'un catalogue figé : énumération des combinaisons, seuil de vérité, départages, et l'assignation qui fige le résultat entre deux pesées. Il décrit aussi les conditions sous lesquelles chaque écran affiche ces objets, et le chemin nu qu'emprunte le rapport PDF.

Entités

Le catalogue n'est pas stocké : LUDIC_ITEMS est une constante du code, 222 entrées, 71 de catégorie objet et 151 de catégorie insolite, de 0,001 kg (« un trombone à papier ») à 200 kg (« un piano droit »). Les noms y sont uniques ; c'est le nom qui sert de clé partout (compteurs, exclusion, retrouvage d'un objet assigné).

La combinaison la plus juste

getBestLudicCombination(weightKg, options) rend la combinaison de 1 ou 2 objets dont la somme des masses s'écarte le moins de weightKg. Un poids nul ou négatif rend un tableau vide, avant toute énumération.

isValidCombo(combo) :
  1 ≤ combo.length ≤ 2
  ET nombre d'insolites ≤ 2
  ET (aucun insolite OU au moins un insolite de masse < 1,0 kg)

passe 1 — objets seuls, i = 0…221 dans l'ordre du catalogue
  si valide : diff = |poids(i) − weightKg|
              si diff < bestDiff        → bestCombo = [i]
passe 1 — paires, i = 0…221, j = i…221
  si valide : diff = |poids(i) + poids(j) − weightKg|
              si diff < bestDiff − 1e-5 → bestCombo = [i, j]

si options : bestCombo = pickByExclusionAndTurnover(...) ?? bestCombo

passe 2 (repli) — seulement si bestCombo est vide : même énumération
  sans isValidCombo

regroupement : les deux entrées de même nom fusionnent en { item, count: 2 }

Le seuil 1e-5 sur les paires est le départage qui fait qu'un objet seul l'emporte sur une paire à justesse égale : la paire doit être meilleure d'au moins un centième de gramme pour passer devant. Entre deux objets seuls, ou entre deux paires, la comparaison est stricte (<) : le premier rencontré dans l'ordre du catalogue gagne.

src/utils/ludicWeight.ts

Cas limites
  • weightKg ≤ 0 → []. Les quatre fonctions publiques (getLudicDecomposition, getLudicEquivalence, getLudicEquivalenceParts, getLudicEmojis) rendent vide sans appeler le moteur : rien à dessiner, rien à dire.
  • Un insolite de 1 kg ou plus seul → combinaison invalide, jamais énumérée. 112 des 151 insolites sont dans ce cas ; il reste 110 objets seuls valides sur 222.
  • Deux insolites de moins de 1 kg → valide (chacun satisfait la clause).
  • Le repli de la passe 2 ne peut jamais s'exécuter : les 71 objets de catégorie objet passent seuls isValidCombo, donc bestCombo n'est jamais vide à la sortie de la passe 1. non implémenté en pratique — le code est mort.
  • Un poids que le catalogue n'approche pas à 200 g près (quelques tonnes) est rendu quand même : la combinaison la plus juste sort, si fausse soit-elle. Le seuil de 200 g ne filtre que le chemin à options.
  • Sans options, la liste candidates n'est jamais remplie : le coût du choix par exclusion et turn-over n'est payé que par les blocs de la home.

Exclusion et turn-over

pickByExclusionAndTurnover ne s'exécute que si withOptions est vrai, c'est-à-dire si options.exclude est non vide ou si options.usage est présent — un objet usage vide suffit à activer le chemin, un exclude vide ne suffit pas.

vraies = candidats dont diff ≤ 0,2 + 1e-5          // 200 g, écart ABSOLU
pool   = vraies dont aucun objet n'est dans exclude
si pool est vide → null (l'appelant garde la combinaison la plus juste)

sinon, réduction sur pool, dans cet ordre :
  1. usage cumulé de la combinaison croissant  (Σ usage[nom], 0 par défaut)
  2. écart croissant, à 1e-5 près
  3. rang d'énumération croissant

Le rang est l'indice de poussée dans candidates : tous les objets seuls valides d'abord (rangs 0 à 109, ordre du catalogue), puis toutes les paires valides (rangs 110 à 10 582, ordre i puis j ≥ i). À usage et écart égaux, un objet seul l'emporte donc sur toute paire.

Le turn-over prime la justesse : une paire d'usage cumulé 0 bat un objet seul d'usage 1, quel que soit l'écart, tant que les deux sont dans les 200 g.

src/utils/ludicWeight.ts

Cas limites
  • Aucune combinaison vraie à 200 g près → vraies vide → pool vide → null : la plus juste sort, l'exclusion et le turn-over sont abandonnés ensemble. Jamais une équivalence fausse pour éviter une répétition.
  • Toutes les combinaisons vraies contiennent un objet exclu → même sortie : la répétition est acceptée.
  • L'usage se compte par combinaison, pas par objet : une paire d'objets vus 0 et 2 fois totalise 2 et cède à un objet seul vu 1 fois.
  • Une paire du même objet compte cet objet deux fois dans le total d'usage.
  • Les paramètres bestDiff et weightKg sont reçus par la fonction et jamais lus.

L'assignation des objets à la pesée

Trois fonctions, un seul appelant. useLudicAssignment(weightHistory) est appelé par useAppData, donc à chaque changement du journal quel que soit l'écran ouvert ; les homes et la carte de confirmation ne font que lire son résultat.

latestWeighInSignature(history) :
  la plus récente = max sur `${date}T${time ?? '00:00'}` (comparaison de chaînes,
                    strictement supérieur : à égalité, la première rencontrée reste)
  aucune ligne → 'aucune-pesee'
  sinon        → `${id}|${date}|${time ?? ''}`

resolveLudicAssignment(signature, totalLoss, lastLoss) :
  total10 = round(totalLoss × 10) / 10 ; last10 = idem
  videAlorsQuePositive = conservée ET ((total10 > 0 ET total vide)
                                    OU (last10  > 0 ET last  vide))
  CONSERVER si conservée ET !videAlorsQuePositive
              ET signature identique ET totalKg === total10 ET lastKg === last10
  SINON :
    total = getLudicDecomposition(totalLoss, { usage: counts })
    last  = getLudicDecomposition(lastLoss,  { usage: counts,
                                               exclude: noms de total })
    isNew = true

commitLudicAssignment(assignment) :   // appelée sous useEffect si isNew
  si assignment.signature ≠ signature écrite :
     counts[nom] += 1 pour chaque entrée de total puis de last
  écriture systématique de { counts, assignment } sous glow_ludic_usage

Deux identités distinctes : la signature (la ligne la plus récente) commande les compteurs ; la signature et les deux pertes au dixième commandent la conservation. Une correction sur une pesée passée change les pertes sans changer la signature : elle réassigne sans compter.

« Depuis le début » est résolu en premier et sert d'exclude à la dernière perte : c'est la dernière perte qui cède.

src/utils/ludicUsage.ts, src/utils/useLudicAssignment.ts, src/app/useAppData.ts

Cas limites
  • Journal vide → signature 'aucune-pesee', pertes 0, deux listes vides, aucun compteur touché (les boucles ne parcourent rien).
  • totalKg ou lastKg absents (assignation écrite avant le 2026-08-16) → la comparaison à undefined échoue → réassignation, une fois.
  • Liste vide alors que la perte correspondante est positive → réassignation, même signature inchangée : une tuile ne peut pas rester sans image.
  • Liste vide alors que la perte est nulle ou négative → conservée : c'est le cas légitime.
  • L'incrément vaut +1 par entrée, pas par exemplaire : « 2 balles de jonglage » compte 1.
  • Si l'exclusion a cédé (aucune vraie sans objet exclu), le même nom peut figurer dans total et dans last : il prend alors +2 au même commit.
  • L'heure manquante vaut '00:00' pour le tri mais chaîne vide dans la signature : deux lignes ne diffèrent jamais par ce défaut, puisque l'identifiant les sépare déjà.
  • Le tri du plus récent se lit sur date/time, jamais sur l'ordre d'insertion : une pesée antidatée ne devient pas la dernière.

Les deux pertes

weightOverview(weightHistory) produit les deux nombres que l'assignation consomme. Convention : positif = perte.

startingWeight = poids de la ligne portant isStartingWeight === true, sinon 0
sorted         = weightHistory trié par date+heure DÉCROISSANTE
currentWeight  = sorted[0].weight, ou startingWeight si le journal est vide
totalLoss      = startingWeight − currentWeight
lastLoss       = sorted.length ≥ 2 ? sorted[1].weight − sorted[0].weight : 0
hasOnlyStartingWeight = journal vide
                     OU (une seule ligne, marquée isStartingWeight)
                     OU totalLoss ≤ 0

Le poids de départ se reconnaît au drapeau isStartingWeight, jamais à sa valeur ni à sa place dans le journal.

src/features/home/homeOverview.ts, src/shared/model/startingWeighIn.ts

Cas limites
  • Moins de deux pesées → lastLoss = 0, donc aucun bloc « dernière perte ».
  • Reprise de poids → totalLoss ou lastLoss négatif ; le moteur rend une liste vide et les écrans se taisent.
  • Aucune ligne marquée départ → startingWeight = 0, donc totalLoss négatif dès la première pesée : tout se tait.
  • Les soustractions sont flottantes : 96,0 − 88,6 vaut 7,400000000000006. L'arrondi au dixième n'intervient que pour l'identité de l'assignation et pour l'affichage.

Le dessin de la composition

LudicComposition reçoit une liste de DecomposedLudicItem et rend au plus deux images.

liste absente ou vide → null (rien n'est rendu, pas même un cadre)

à plat : pour chaque entrée, qty = min(count, 2) exemplaires, chacun portant
         key = DESSINS_LUDIQUES[entrée.key] ? entrée.key
                                            : getLudicIllustrationKey(entrée.name)
puis    : slice(0, 2)

rendu d'un exemplaire : le composant de DESSINS_LUDIQUES[key] s'il existe,
                        sinon l'émoji dans un <svg viewBox="0 0 100 100">
                        (fontSize 86, fontes émoji nommées explicitement)

Les deux exemplaires se partagent la largeur (flex-1), écart de 4 px en taille normale et 2 px en taille compacte ; chaque image est en object-contain sur toute la hauteur du cadre fourni par l'appelant. L'attribut title porte le nom de l'objet.

src/versions/mixte/components/LudicComposition.tsx

Cas limites
  • Le plafond min(count, 2) et le slice(0, 2) font double emploi : le moteur ne rend jamais plus de deux exemplaires au total.
  • Une clé conservée qui n'existe plus dans la table est redérivée du nom au rendu, sans attendre une pesée.
  • Ni le nom ni la clé ne donnent de dessin → l'émoji conservé dans l'assignation. Aucun repli sur un objet d'une autre masse.

La clé d'illustration

getLudicIllustrationKey(name) est une chaîne de 68 tests name.includes("…") dans un ordre fixe ; le premier qui passe rend sa clé, sinon 'emoji'. Les sous-chaînes cherchées sont en minuscules.

Deux appelants, deux traitements du nom :

getLudicDecomposition : key = getLudicIllustrationKey(item.name.toLowerCase())
LudicComposition      : key = getLudicIllustrationKey(item.name)   // brut

Sur les 222 objets du catalogue, 65 déclenchent une clé de dessin quand le nom est minusculé, 64 quand il ne l'est pas : « une figurine Funko Pop » ne correspond à "funko pop" que minusculé. La redérivation au rendu ne s'applique qu'aux clés absentes de DESSINS_LUDIQUES, 'emoji' comprise ; une assignation portant déjà funko_pop est donc dessinée normalement. C'est une assignation ancienne, écrite avec 'emoji', que la redérivation devrait réparer et ne répare pas pour ce seul objet : le nom brut ne correspond à aucun test, la clé retombe sur 'emoji'.

src/utils/ludicWeight.ts, src/versions/mixte/components/LudicComposition.tsx

Cas limites
  • DESSINS_LUDIQUES compte 68 entrées, exactement les 68 clés que la fonction sait rendre. Aucune clé produite n'est orpheline de dessin.
  • La clé 'car_battery' figure dans le type LudicIllustrationKey mais n'est renvoyée par aucun test et n'a pas d'entrée dans la table. non implémenté
  • Quatre tests — pasta, water, pack_water, duck — ne correspondent à aucun objet du catalogue actuel : leurs dessins sont inatteignables.
  • Deux tests portent une alternative ("paquet de pâtes" || "pâtes" ; "boule de pétanque" || "pétanque").
  • La détection est par sous-chaîne : renommer un objet du catalogue sans toucher aux tests peut faire basculer son dessin en émoji, ou lui en donner un autre.

La carte de confirmation de pesée

computeSubmissionInfo(afterList, targetDate, type, departKg) décide de quoi parle la carte, WeighInSubmissionCard de ce qu'elle montre. → fonctionnelle

computeSubmissionInfo :
  sorted = afterList trié par date+heure CROISSANTE ; vide → null
  idx    = index de la première ligne dont date === targetDate,
           sinon dernière ligne
  previousWeight = poids de sorted[idx − 1], ou departKg s'il n'y en a pas
  lossSinceLast  = previousWeight − poids(idx)
  lossSinceStart = departKg − poids(idx)
  isMostRecent   = idx === sorted.length − 1
  hasPreviousLogs = idx > 0
  isStartingWeight = drapeau de la ligne visée

WeighInSubmissionCard :
  heightM = profile.height / 100
  subBmi  = heightM > 0 ? poids / heightM² : 22        // NON arrondi
  insolite = subBmi ≥ 19 ET lossSinceStart > 0
             ET isMostRecent ET !isStartingWeight
  bloc « dernière perte enregistrée » si insolite ET hasPreviousLogs
             ET lossSinceLast > 0
             ET lossSinceLast.toFixed(1) ≠ lossSinceStart.toFixed(1)
  bloc « Depuis le début » si insolite (la condition lossSinceStart > 0
             y est retestée, elle est déjà dans insolite)

objets d'un bloc — assignedItemsFor(loss, assignedKg, assigned) :
  assignedKg !== undefined ET round(loss × 10)/10 === assignedKg
     → assigned                       (les objets de l'assignation)
     → sinon getLudicDecomposition(loss)   // sans usage ni exclude

Le bouton OK n'existe que dans le bloc insolite ; sans lui, seule la croix ferme la carte.

src/features/weight/submissionInfo.ts, src/versions/mixte/features/weight/WeighInSubmissionCard.tsx

Cas limites
  • Taille inconnue ou nulle → subBmi = 22, donc jamais bloquant. La home, elle, prend bmiOf qui rend 0 dans le même cas et bloque : les deux écrans divergent quand la taille manque.
  • subBmi n'est pas arrondi ; un IMC de 18,97 bloque ici alors que bmiOf l'arrondirait à 19,0 et laisserait passer la home.
  • Les deux pertes égales au dixième → seul « Depuis le début » paraît.
  • Pesée déplacée dans le passé par une édition → isMostRecent faux → aucun bloc.
  • Édition du poids de départ → isStartingWeight vrai → aucun bloc.
  • Reprise de poids → lossSinceStart ≤ 0 → aucun bloc, même sur la pesée la plus récente.
  • La recherche de la ligne visée se fait sur la date seule (une pesée par jour) ; date absente du journal après écriture → repli sur la dernière ligne.
  • Le recalcul de secours passe sans options : il peut nommer un autre objet que la home pour le même nombre.

Les tuiles de perte des homes

Les deux homes calculent les mêmes trois booléens, à partir de weightOverview et de bmiOf. → fonctionnelle

bmiOf(poids, tailleCm) = tailleCm > 0
                         ? round(poids / (tailleCm/100)² × 10) / 10
                         : 0
isBmiLow      = bmi < 19
showLastLoss  = !isBmiLow ET lastLoss  > 0 ET !hasOnlyStartingWeight
showTotalLoss = !isBmiLow ET !hasOnlyStartingWeight ET totalLoss > 0

home standard seulement :
lossesEqual   = showLastLoss ET showTotalLoss
                ET lastLoss.toFixed(1) === totalLoss.toFixed(1)

ordre de rendu, home standard :
  emplacement de la dernière perte :
     lossesEqual ? tuile « Depuis le début » : showLastLoss && tuile dernière perte
  plus bas :
     showTotalLoss && !lossesEqual && tuile « Depuis le début »

Sur la home sections, lossesEqual n'existe pas : deux pertes égales gardent leurs deux mini-tuiles. Les tuiles y sont des candidates de la rangée Progrès, rangs 3 (perte totale) et 4 (dernière perte), coupées à PROGRES_MAX = 4 tuiles par rang croissant.

Cas limites
  • Taille inconnue → bmi = 0 → isBmiLow vrai → aucune tuile sur aucune home.
  • hasOnlyStartingWeight englobe déjà totalLoss ≤ 0 : le test totalLoss > 0 de showTotalLoss est redondant.
  • Dernière perte positive mais perte totale négative → hasOnlyStartingWeight vrai → les deux tuiles se taisent.
  • Sur la home standard, quand lossesEqual est vrai, la tuile « Depuis le début » occupe la place de la dernière perte, donc plus haut que d'ordinaire.
  • La home standard est tenue pour morte depuis le 2026-08-31 : ses conditions ne bougent plus.

Le repli du dessin sur la home sections

La home sections ne fait pas confiance à l'assignation conservée quand elle est vide alors que la perte ne l'est pas.

ludicTotal = (ludic.total.length > 0 OU totalLoss ≤ 0)
             ? ludic.total
             : getLudicDecomposition(totalLoss)              // sans options

ludicLast  = (ludic.last.length > 0 OU lastLoss ≤ 0)
             ? ludic.last
             : getLudicDecomposition(lastLoss, {
                 exclude: noms de ludicTotal })              // avec options

Le repli de la perte totale part sans options : ni filtre à 200 g, ni turn-over, la combinaison la plus juste sort. Le repli de la dernière perte porte un exclude non vide, ce qui active pickByExclusionAndTurnover : le filtre des 200 g s'applique, le turn-over est neutre puisque usage est absent et que tous les cumuls valent 0 — le départage tombe donc sur l'écart, puis sur le rang.

Le repli ne choisit jamais à la place de l'assignation : tant qu'elle porte des objets, c'est elle qui est lue, et rien n'est écrit en retour.

Cas limites
  • Assignation vide et perte nulle ou négative → liste vide gardée, LudicComposition ne rend rien, mais la tuile est de toute façon masquée par showLastLoss / showTotalLoss.
  • Les objets du repli ne sont ni comptés ni mémorisés : ils changent au prochain rendu si l'assignation, elle, se répare.
  • La garde de resolveLudicAssignment couvre déjà ce cas ; ce repli est le second filet, indépendant de ce qui est écrit sur l'appareil.

La durée d'une perte

Deux fonctions : lossSpanDates donne les bornes, lossSpanLabel les écrit. → fonctionnelle

lossSpanDates(weightHistory) :        // sorted = tri date+heure DÉCROISSANTE
  totalFrom = date de la ligne portant isStartingWeight
  totalTo   = date de sorted[0]
  lastFrom  = date de sorted[1]
  lastTo    = date de sorted[0]

lossSpanLabel(debut, fin) :
  debut absent OU debut > fin              → null
  jours = daysBetween(debut, fin)          // round(ΔUTC / 86 400 000)
  jours < 1                                → null
  jours < 7                                → `en ${max(1, jours)} jour(s)`
  sinon    semaines = max(1, round(jours / 7))
                                           → `en ${semaines} semaine(s)`

appel : lossSpanLabel(spans.totalFrom, spans.totalTo ?? aujourd'hui)
        lossSpanLabel(spans.lastFrom,  spans.lastTo  ?? aujourd'hui)

La durée est l'écart entre les deux pesées comparées, jamais l'écart à aujourd'hui : le repli sur la date du jour ne joue que si le journal est vide, auquel cas la borne de début manque aussi et le résultat est null.

src/features/home/homeOverview.ts, src/shared/date/date.local.ts

Cas limites
  • Deux pesées le même jour → 0 jour → null, aucune durée écrite.
  • Pesée de départ postérieure à la plus récente (départ antidaté à l'envers) → debut > fin → null.
  • Aucune ligne marquée départ → totalFrom absent → null.
  • Une seule pesée → sorted[1] absent → lastFrom absent → null.
  • 13 jours → round(13/7) = 2 → « en 2 semaines » ; 7 jours → « en 1 semaine » ; 3 jours → « en 3 jours ».
  • daysBetween compte en UTC à partir des seules dates : les heures et les changements d'heure n'entrent pas dans le calcul.

Camille : départ le 4 mai 2026, dernière pesée le 12 septembre → 131 jours → round(131/7) = 19 → « en 19 semaines ». Dernière perte, du 5 au 12 septembre → 7 jours → « en 1 semaine ».

L'équivalence dépliée

Le bloc déplié de la home sections est rendu dans un portail par-dessus l'écran téléphone, conditionné par l'état d'ouverture et par les mêmes booléens que les tuiles. → fonctionnelle

ouvert = openEquivalences.total_loss OU openEquivalences.last_loss
si ecranTelephone ET ouvert :
   openEquivalences.total_loss ET showTotalLoss
      ? bloc « Depuis le début »
      : bloc « dernière perte enregistrée »

openEquivalences est un état local à deux booléens indépendants, initialisé depuis glow_home_equivalences (chaque champ lu en === true, tout le reste vaut faux) et réécrit sous cette clé à chaque changement. Un clic sur une tuile bascule son booléen ; la croix du bloc remet le sien à faux ; un clic sur le voile, comme la fermeture générale des couches (useFermetureCouche), remet les deux à faux. Les deux peuvent être vrais en même temps, mais un seul bloc est rendu, et c'est la perte totale qui l'emporte.

Le bloc reprend le libellé, signedKg(−perte), « soit l'équivalent de », la même LudicComposition et le même LudicEquivalenceText que la tuile — donc les mêmes listes ludicTotal / ludicLast, repli compris.

  • Hors écran téléphone (ecranTelephone nul), rien n'est rendu, quel que soit l'état mémorisé.

La valeur affichée est alors weights.lastLoss, et LudicComposition ne rend rien si la liste est vide.

L'équivalence dans le rapport PDF

La phrase est écrite dans la section II, sous le paragraphe des pesées. → fonctionnelle

sortedWeights = pesées de la période, triées par date+heure croissante
firstW = sortedWeights[0].weight        // null si aucune
lastW  = dernière.weight
periodDelta = lastW − firstW            // NÉGATIF quand la période est une perte

si include.weights :
   titre « II. Poids et doses »
   si sortedWeights est non vide :
      paragraphe « Première pesée de la période : … Dernière : … Variation : … »
      delta = periodDelta ?? 0
      si include.insolites ET delta < 0 :
         paragraphe italique, gris, corps 8 :
         `Soit l’équivalent de : ${getLudicEquivalence(−delta)}.`
      graphe poids/doses
   sinon :
      « Aucune pesée enregistrée sur cette période. »

getLudicEquivalence est appelée sans options : pas de filtre à 200 g, pas de turn-over, pas d'exclusion, aucune lecture ni écriture de l'assignation. L'objet du PDF peut donc différer de celui de la home pour la même valeur.

La variation est celle de la période (dernière moins première pesée de la fenêtre), pas la perte depuis le poids de départ.

Cas limites
  • include.weights faux → pas de section II du tout, donc pas de phrase, même case insolites cochée.
  • Période sans pesée → phrase d'absence, pas d'équivalence.
  • Une seule pesée sur la période → firstW === lastW → delta = 0 → pas de phrase.
  • Reprise de poids sur la période → delta > 0 → pas de phrase.
  • L'apostrophe de « l’équivalent » est typographique (U+2019).

La case insolites et le masque des données

Chaque section du rapport est produite si sa case est cochée et si la période porte la donnée correspondante. La case insolites échappe à la seconde moitié.

available = {
  weights: filteredWeights.length > 0,
  meals:   foodTrackingEnabled ET ≥ 1 repas sur la période,
  sideEffects: isModuleOn(profile, 'symptoms') ET ≥ 1 effet,
  steps:   stepsTrackingEnabled ET ≥ 1 relevé > 0,
  sport:   sportTrackingEnabled ET ≥ 1 séance,
  sleep:   sleepTrackingEnabled ET ≥ 1 entrée,
  meTime:  false,          // écarté du chemin court, masqué par hasMeTimeData
  insolites: false,        // n'est pas une donnée
}

effective = {
  weights: selection.weights ET available.weights,
  …
  meTime:  selection.meTime ET hasMeTimeData,
  insolites: selection.insolites,        // AUCUN masque
}

La bascule insolites est rendue sans garde, à la différence des modules, dont la bascule disparaît quand le module est éteint ou la période muette. available.insolites n'entre donc dans aucun calcul : c'est un reliquat de l'export rapide, supprimé le 2026-08-25 — il n'existe plus qu'un seul chemin, l'export sur mesure.

La ligne « Les équivalences insolites » entre dans le sommaire de l'écran d'attente dès que la case est cochée, sans autre condition.

Défauts et mémorisation du sur-mesure

Les cases de l'export sur mesure sont mémorisées sous glow_report_include_v2.

DEFAULT_INCLUDE = { weights: true, meals: true, sideEffects: true,
                    steps: true, sport: true, sleep: true,
                    meTime: false, insolites: true }

état initial : { ...DEFAULT_INCLUDE, ...(getItem('glow_report_include_v2') ?? {}) }

bascule d'un champ :
   next = { ...include, [champ]: !include[champ] }
   setInclude(next) ; setItem('glow_report_include_v2', next)

La fusion avec les défauts fait qu'un champ ajouté après coup n'est jamais absent d'une valeur déjà stockée. Le suffixe _v2 de la clé a été posé le 2026-08-25 pour que le renversement des défauts — insolites passant de décoché à coché — soit vu au moins une fois par les appareils déjà réglés ; l'ancienne clé n'est ni lue ni effacée.

src/versions/mixte/components/MedicalReportExport.tsx

Cas limites
  • Rien en mémoire → les défauts s'appliquent : la case insolites est cochée.
  • Valeur stockée partielle → seuls les champs présents écrasent le défaut.
  • L'écriture porte l'objet entier à chaque bascule : un champ absent du stockage y entre à la première modification d'une autre case.
  • localStorage indisponible → getItem rend null et setItem échoue en silence : les défauts reviennent à chaque ouverture.

Aucune décision V2 ne porte sur ce domaine : ni GUIDELINES.md ni src de la V2 ne mentionnent les équivalences insolites.
